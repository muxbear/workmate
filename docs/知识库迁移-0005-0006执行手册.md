# 知识库迁移 0005 / 0006 执行手册

> 适用：把「迭代 6」的知识库分支发布到线上之前。
> 状态（2026-09-26）：**已在真实库上完成往返演练与只读回填预测，未执行 `--apply`**。

## 为什么必须做（顺序不能反）

代码已经依赖这两项迁移，**不是可选的收尾**：

| 迁移 | 加了什么 | 谁在依赖它 |
| --- | --- | --- |
| `0005` | `knowledge_base_documents.parse_warning` | `doc_service.py:306` 把它写进文档的 UPDATE（每一轮索引进度落库都会带上这一列） |
| `0006` | `knowledge_base_entities.name_key`、`knowledge_base_relations.from_key/to_key` + 2 索引 | `graph_service.py:209` 的 `name_key_expr` 与归一后的全部读写路径 |

**必须先迁移、再发布代码。** 反过来（先发代码）会让未迁移的库在索引进度落库与图谱查询处
报 `column does not exist`——索引会卡在中间态，图谱页签直接打不开。

反过来是安全的：这两个迁移只**新增可空列与索引**，正在运行的旧代码不认识这些列，不受影响。
所以不存在"迁移与发布必须同一瞬间"的约束，可以间隔。

## 一、执行前

```bash
cd web/backend

# 1) 看状态：0005 / 0006 应为「待应用」，且两者都有回滚脚本
uv run python scripts/migrate.py --status

# 2) 记下三个行数，执行后要对照
#    （2026-09-26 的实测基线：knowledge_bases=2 / documents=8 / entities=288）
```

可选但推荐：跑一次 `--dry-run`，它在事务里试跑后回滚，能在**真实数据**上验证 SQL 能否通过。

## 二、执行

```bash
uv run python scripts/migrate.py --apply
```

规模与耗时：`UPDATE` 触及 **288** 行实体与 **85** 行关系；两条索引建在小表上。
整批是秒级操作，不涉及向量库、**不需要重建索引**。

## 三、执行后核对

```sql
-- 1) 四个新列都在
SELECT table_name, column_name FROM information_schema.columns
 WHERE table_name IN ('knowledge_base_documents','knowledge_base_entities','knowledge_base_relations')
   AND column_name IN ('parse_warning','name_key','from_key','to_key');

-- 2) 两条索引都在
SELECT indexname FROM pg_indexes
 WHERE indexname IN ('ix_kb_entities_kb_name_key','ix_kb_relations_kb_from_to_key');

-- 3) 回填到位：不应有 NULL / 空串（预期 288 行实体、85 行关系全部有键）
SELECT count(*) FILTER (WHERE name_key IS NULL OR name_key = '') AS 实体缺键
  FROM knowledge_base_entities;
SELECT count(*) FILTER (WHERE from_key IS NULL OR to_key IS NULL) AS 关系缺键
  FROM knowledge_base_relations;

-- 4) 归一生效：分组数应为 281（此前 288 行是"大小写各占一个节点"的分裂状态）
SELECT count(DISTINCT name_key) AS 实体节点数 FROM knowledge_base_entities;

-- 5) 版本记录
SELECT version FROM schema_migrations ORDER BY version;   -- 应含 0005、0006
```

界面核对：打开知识库 → 图谱页签，确认 `LangChain` 与 `langchain` **合成一个节点**、
节点大小按「N 篇文档」显示、关系条数为 84。

## 四、回滚

```bash
uv run python scripts/migrate.py --rollback 2     # 回滚最后 2 个（0006、0005）
```

回滚只**丢弃新列与索引**，不动实体/关系数据本身——归一键是派生值，由 `name`/`from_entity`
现算得出，丢掉不损失信息，需要时重跑迁移即可重建。

2. **只读回填预测**（用真实的 Postgres 函数算，不做任何写入）：

   | 指标 | 实测 | 先前 SQLite 模拟 |
   | --- | --- | --- |
   | 实体行数 → 分组数 | 288 → **281** | 281 ✓ |

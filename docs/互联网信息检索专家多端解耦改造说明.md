# 互联网信息检索专家多端解耦改造说明

> 版本：v1.0　编制日期：2026-09-29
> 适用范围：桌面版（`desktop/`，ke-work）、Web 版（`web/`，ke-hermes）、移动版（`mobile/`，复用 Web 后端）
> 关联模块：专家体系（`experts` 表 / `BUILTIN_EXPERTS`）、专家能力契约、MCP 服务「联网搜索」、专家同步下发
> 关联文件：`packages/expert-contract/contract.json`、`docs/视频创作专家多端业务梳理与改造方案.md`、`docs/文档写作专家多端业务梳理与改造方案.md`

---

## 0. 结论摘要

**一句话结论**：`web.search` 与 `knowledge.search` 同类——**三端都不需要端侧实现**，统一由服务端「联网搜索」MCP 服务承载。本次把该专家从"界面上手工建的一条库内记录"升级为**代码即权威定义的内置专家**（能力声明 + 平台化提示词 + 版本化下发），并顺手补上了检索链路唯一真正的短板：**单一数据源失效时没有可用的回退**。

改造前它已是"能同步到三端"的形态（`+` 菜单可见、MCP 关联存在），但：

| 维度 | 改造前 | 改造后 |
| --- | --- | --- |
| 定义来源 | 只在 DB（2026-09-01 手工创建，`undeletable=false`） | `BUILTIN_EXPERTS` 内置项，每次启动幂等落库（id 不变） |
| `system_prompt` | **一句话**：「你是一名互联网信息检索专家，擅长根据用户问题调用联网搜索工具获取并整理互联网信息。」 | 平台中立模板（含 `{{platform_notes}}`）：检索预算 / 检索策略 / 引用纪律 |
| `prompt_template` | 空 → 桌面端输入框文案回落到渲染层本地硬编码模板 | 服务端下发委派模板（要求原样保留来源链接） |
| 能力声明 | 无显式声明，靠 MCP 服务名反推 | `capabilities: ["web.search"]`（与兄弟专家同款声明式） |
| 版本号 | `1.0.0` 之后不再变化 | `1.1.1`，种子按**只增不减**推进（驱动桌面端重新同步） |
| 检索数据源 | Tavily（配额耗尽即返回空结果）+ DuckDuckGo（本网络不可达） | **Tavily → Bing → DuckDuckGo 可配置回退链** |

## 1. 现状与根因

### 1.1 为什么它不在代码里

`BUILTIN_EXPERTS`（`web/backend/src/api/experts/service.py`）此前只有文档写作 / 视频创作 / 云知识库检索三个内置专家。该专家创建于 2026-09-01，早于 2026-09-22 的"专家契约 + 平台化渲染 + 能力声明"改造，因此停留在旧形态：**记录在库里、定义不在代码里**，既享受不到平台化渲染，也没有版本化下发（种子的字段更新不会推进 `version`，而桌面端 `shouldUpdateExpert` 只在服务端版本更高时才覆盖本地副本 → 改造对桌面端不可见）。

### 1.2 检索链路真正断在哪（本次实测）

| 数据源 | 实测结果（2026-09-29） |
| --- | --- |
| Tavily | API 可达但**配额已耗尽**：`This request exceeds your plan's set usage limit` |
| DuckDuckGo | `html.duckduckgo.com` / `duckduckgo.com` 均 **ConnectTimeout**（本网络不可达） |
| Bing | 可达：`https://www.bing.com/search?q=…` → 200，约 100 KB，10 个 `<li class="b_algo">` 结果块 |
| 内置 `tavily_search`（后端工具） | 失败时**只返回空结果、无回退**（`agent/tools/tavily_search.py`） |
| MCP `web_search`（联网搜索服务） | 有回退，但只回退到 DuckDuckGo → 在本网络同样拿不到数据 |

**结论：改造前该专家在三端都检索不到任何数据。** 这不是改造引入的问题，而是"唯一数据源 + 唯一回退都不可用"。

## 2. 改造内容

### 2.1 决策 D1：`web.search` 只走 MCP，不绑定内置工具

能力映射由 `CAPABILITY_BUILTIN_TOOLS[web.search]: ("tavily_search",)` 改为 **`()`**：

- **Web**：`_declared_tool_names` 为空 → 不产生 `expert_tools` 关联 → `skip_capabilities` 为空 → 「联网搜索」MCP 服务**不被跳过**，专家子代理拿到 `mcp__联网搜索__web_search`（本进程自托管，走内存传输，无网络跳）；
- **桌面**：`web.search` 不映射任何本地工具 → 走 `mcpConfigs` 装配 `web_search`（与改造前一致）；
- **移动**：复用 Web 后端，零改动。

为什么不复用内置 `tavily_search`：它是**单源**工具，且一旦绑定本能力，`_resolve_entity_tools` 的 skip 判据会把 MCP 服务顶掉——等于把唯一有多源回退的实现换成了没有回退的那个。这与 `CAPABILITY_VIDEO_GENERATE: ()` 是同一类做法（`video.generate` 也只走 MCP）。

### 2.2 决策 D2：专家定义进代码，与兄弟专家同构

`BUILTIN_EXPERTS` 新增「互联网信息检索专家」：`capabilities: ["web.search"]`、`mcp_tool_name: "联网搜索"`、`prompt_template`（新委派模板）、平台中立 `system_prompt`。提示词只讲"怎么做检索"与"怎么给可核验的答案"，**不含任何端侧命令、路径或工具前缀**（工具按后缀 `web_search` 识别，前缀由平台适配层决定，与云知识库检索专家同款写法）。

提示词要点：

1. **检索预算**：整个任务最多 8 次检索，达到上限就用手头信息作答并说明覆盖范围；
2. **检索策略**：按问题类型拟定可命中原文的关键词（而不是丢整句话）；中英各试；动态型问题带时间限定；命中导航站/聚合页就换更具体的词；矛盾时按来源权威性与时效判断；
3. **回答要求**：先结论后依据、每条关键事实带来源（标题 + 链接）、严禁编造、只有摘要时明确声明未核实原文、标注时效与推断、不写文件（除非委派明确要求文档）。

### 2.3 决策 D3：检索提供方回退链（可配置）

`mcp_servers/web_search_server.py` 由"Tavily → DuckDuckGo 二选一"改为**按配置顺序逐家尝试**：`WEB_SEARCH_PROVIDERS`（默认 `tavily,bing,duckduckgo`），前一家无结果/失败就试下一家，全部失败才返回**汇总了各家原因**的 `error`。

- 新增 **Bing 解析器**（`parse_bing_results`）：按 `<li class="b_algo">` 分块取 `<h2><a href>` 的 URL/标题 + `b_lineclamp*` 段落的摘要；协议相对地址补全；`/ck/a` 跳转壳尽量还原真实 URL；无标题或无链接的块直接丢弃（引用里不能出现坏链接）；
- 默认把 **Bing 排在 DuckDuckGo 之前**：DDG 在部分网络（含国内）不可达，排前面会白吃一次连接超时；DDG 仍保留为最后一档；
- 新增配置：`WEB_SEARCH_PROVIDERS` / `WEB_SEARCH_TIMEOUT_SECONDS`（`.env.example` 已同步）；
- 返回结构不变（`{query, results[{title,url,snippet}], total, source, error?}`），新增 `attempts` 记录实际尝试过的提供方顺序（便于定位哪一层不可用）。

### 2.4 决策 D4：版本只增不减

种子（`seed_builtin_experts`）此前只更新字段、**不碰 `version`**。新增 `is_newer_version()`：内置项声明了版本且**高于**当前值时才写入。既能把定义变更推给各端重新同步，也不会把界面上手工调高的版本号回退掉。

### 4.2 Web 端实机（登录 wangke，`/experts` + `/chat`）

1. 专家卡片：`v1.1.1`、分类「AI工具专家」、新描述与新标签正常渲染；
2. `+` 菜单「专家」子菜单列出该专家，选中后输入框出现专家 chip；
3. 提问「Anthropic 的 Opus 5.5 是什么时候发布的？主要升级点是什么？」→ 后端日志确认链路：

```
为 Expert 8e6b04ee-… 加载了 1 个 MCP 工具          ← 只声明能力即拿到 web_search（内存传输）
已为专家「互联网信息检索专家」注入强制委派指令      ← 请求级强制委派生效
Tavily search unavailable, trying the next provider ← 配额耗尽，自动换下一家
GET https://www.bing.com/search?q=… → 200           ← Bing 回退命中
```

4. 回答质量符合提示词要求：结论先行、每条事实带来源、显式区分推断、**列出未能核实的信息（不编造）**、说明检索覆盖范围；
5. 引用链接为真实可点的 `<a href>`，抽查两条均返回 **200**（`anthropic.com/claude-opus-5-5`、`caixin.com/2026-09-23/102487971.html`）；
6. **检索预算生效**：narrow 问题恰好用满 8 次检索后停止并作答（首轮宽问题无预算约束时曾连查 47 次 / 耗时 8 分钟，故补了这条约束）。

## 5. 未覆盖 / 遗留

| 项 | 说明 |
| --- | --- |
| MCP 端到端 | app 内端到端链路**已跑通**（4.3）。Bing 可达且命中稳定，但 DuckDuckGo 在本网络仍不可达；若目标部署环境连 Bing 也不可达，需要按 `WEB_SEARCH_PROVIDERS` 再挂一家（或在「模型/提供商」侧配可用的 Tavily 配额）。 |
| 存量 MCP 连接参数 | 「联网搜索」的 `McpTool.transport` 与专家组里的 `config` 仍是历史遗留的 `sse` 形态（地址指向已挂载的 `/mcp/web-search/sse`）。三端实际都不受影响：Web 走本进程自托管的内存传输，桌面端 `resolveEndpoint` 优先取 `streamableHttpUrl`（配置基址推导，已实测取件成功）。`_ensure_expert_mcp_link` 按既有契约"只补启用位、不覆盖用户改过的地址"，未强行改写。 |
| 内置 `tavily_search` 工具 | 仍是单源、无回退（`test_tavily_search.py` 的 16 条用例钉的是 Tavily 真 API 语义）。本次让专家链路绕开它，其它直接引用该工具的智能体仍会在配额耗尽时拿到空结果，是否统一加固另议。 |
| 桌面端「深度研究」chip | 已接入该专家；若后续另建「深度研究专家」，需重新指认这个映射。 |
| 检索质量 | 检索质量受 Bing HTML 结构影响（页面改版会削弱解析）。已在提示词里加了"命中导航站/聚合页就换更具体的词"的对策，并保留 DuckDuckGo 作为末位回退。 |

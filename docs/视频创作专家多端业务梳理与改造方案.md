# 视频创作专家多端业务梳理与改造方案

> 版本：v1.0　编制日期：2026-09-22
> 适用范围：桌面版（`desktop/`，ke-work）、Web 版（`web/`，ke-hermes）、后续移动版（`mobile/`）
> 关联模块：专家体系、输入卡「+」菜单、Agent 运行时、MCP 视频服务、沙箱、会话产物（artifact）、物化/回灌、文件预览、打包下载
> 关联文件：`packages/expert-contract/contract.json`、`docs/文档写作专家多端业务梳理与改造方案.md`、`docs/移动端复用Web后端接入说明.md`

## 0. 结论摘要

**一句话结论**：视频创作专家的「能力通道」已经建好（MCP 视频生成服务、SSE 产物事件、物化存储、打包接口都已在位），但它**没有接入 2026-09-22 建立的那套专家契约与产物流水线**——专家提示词是桌面端硬编码、素材工具只支持图片、Web 端没有任何视频预览实现。结果是：**两端在"把 video_url 变成磁盘上的成片"这一步都断链**（桌面端默认分类下没有 `execute` 工具、Web 沙箱没有 `curl.exe`），**且 Web 端即使拿到成片也无法预览**。

需求达成度现状：

| 需求 | 桌面版 | Web 版 | 说明 |
| --- | --- | --- | --- |
| ① 输入框「+」可添加视频创作专家 | ✅ 已通 | ✅ 已通 | 两端「+」菜单均可见「视频创作专家」，走同一套专家同步 |
| ② 按用户要求生成文章并正确显示视频 | ❌ 默认路径断链 | ❌ 不通 | 桌面：默认分类 `work` → `filesystem` 后端 → **无 `execute` 工具**，提示词依赖的 `mkdir`/`curl.exe` 无法执行（仅切到「代码」分类才可能）；Web：Linux 沙箱没有 `curl.exe`，且**前端完全没有视频预览链路** |
| ③ 文章 + 视频可打包下载 | ⚠️ 通道已通、前提未满足 | ⚠️ 部分 | 桌面导出通道与 Web `bundle.zip` 都能打包目录，但前提是成片已经落到工作区/交付目录（即需求 ② 先成立）；Web 另有"只读宿主 staging、留存期清理后 404"的问题 |
| ④ 专家与端解耦、可扩展移动端 | ❌ 不成立 | ❌ 不成立 | 提示词含 `curl.exe`/PowerShell/反斜杠，零模板占位符，无 `capabilities` 声明 |

已确认决策（详见第 4 章）：

| 编号 | 决策 | 理由 |
| --- | --- | --- |
| **D1** | 成片落盘统一走素材工具 `download_asset`（各端代理下载），禁止让模型执行平台命令下载 | 视频与图片共用同一条"下载 → 落盘 → 登记 → 物化"流水线，平台差异归零 |
| **D2** | 视频专家提示词按「文档写作专家」的同款规范平台中立化（补 `{{platform_notes}}` / `{{delivery_dir}}` / `{{asset_tool}}`） | 复用已验证的渲染机制，不引入第二套约定 |
| **D3** | 视频专家补齐 `capabilities: ["video.generate", "document.assemble"]` | 由能力驱动启用各端本地工具（含 `download_asset`），不再依赖工具名反推 |
| **D4** | Web 端补齐"与图片对称"的视频预览链路（blob 鉴权方案，复用图片的成熟做法） | 与桌面端已实现的方案保持同构，避免第二套安全模型 |
| **D5** | `bundle.zip` 改为「持久层优先、staging 兜底」并改为流式响应 | 修掉留存期清理后打包 404，同时避免大视频撑爆内存 |
| **D6** | MCP 服务基础地址配置化，同步给客户端时给可达地址 | 视频在桌面端**没有本地替代实现**（图片有 `image_generate`），MCP 不可达 = 功能完全不可用 |

## 1. 背景与目标

### 1.1 现状（需求方描述）

- 桌面版「新建任务」页面：消息输入框左下角「+」可添加「视频创作专家」；文章写完后在**工作区**生成文章与同名文章目录，目录中保存文章的视频。
- Web 版「对话」页面：同样的「+」也可添加「视频创作专家」；文章与视频**保存在沙箱**中，已有"物化存储 → 预览时回灌沙箱"的机制，但该机制目前仍存在问题。

### 1.2 需求

1. 「视频创作专家」既可添加到桌面版「新建任务」，也可添加到 Web 版「对话」的输入框；
2. 两端添加后，按用户输入的要求生成文章，并**正确显示文章中的视频**；
3. 生成的文章与文章视频**可以打包下载**；
4. 「视频创作专家」**不能与桌面版、Web 版耦合**，必须独立，且能同时适配两端，后续还要适配移动端。

### 1.3 目标

- 专家定义（数据库中的一行）与任意端解耦：不含路径分隔符、shell 命令、平台目录约定；
- 两端共用同一条「生成 → 落盘 → 登记 → 物化 → 预览 → 打包」流水线，只有"怎么落盘/怎么显示"由平台适配层决定；
- 移动端接入时**专家定义、能力声明、交付物契约零改动**。

## 2. 现状业务链路梳理

### 2.1 专家定义的唯一来源

专家是**数据库里的一行**，唯一权威定义在 Web 后端种子数据：

- `web/backend/src/api/experts/service.py:871` `BUILTIN_EXPERTS`，包含「文档写作专家」（871-923）与「视频创作专家」（924-985）；
- 启动时由 `seed_builtin_experts`（`service.py:1023`）写入 `experts` 表，并按 `mcp_tool_name` 关联 MCP 服务（`expert_mcp_configs`）；
- 桌面端**没有本地专家种子**，通过 `ExpertSyncService.sync()` 调 `GET /api/expert-sync/list?platform=desktop`（`desktop/src/main/experts/ExpertSyncService.ts:177`）拉取并落到 `~/.ke-work/experts/experts.json`；
- 同步接口的平台参数是契约白名单（`web/backend/src/api/experts/sync_api.py:27`），服务端按平台渲染提示词后再下发。

「视频创作专家」在两端的可见性已被端到端验证：`tmp-e2e/desktop-report.json` 的「+」菜单列表里包含 `视频创作专家`（`tmp-e2e/desktop-report.json:16`）。

### 2.2 视频生成能力通道（MCP 服务）

| 项 | 位置 / 值 |
| --- | --- |
| MCP server | `web/backend/src/mcp_servers/video_gen_server.py`（FastMCP `ke-hermes-video-gen`，`:65`） |
| 进程内注册 | `web/backend/src/server.py:37` `register_local_mcp_server('AI 视频生成', video_gen_mcp)` |
| HTTP 挂载 | `web/backend/src/server.py` `/mcp/video-gen-http`（streamable HTTP） |
| 广场种子 | `web/backend/src/api/mcp/service.py:293-314`（`video_generation`，URL 见 `:311-313`） |
| 工具 | `generate_video`（`:481`）、`query_video_generation`（`:531`） |
| 第三方 | 阿里云百炼 `wan3.0-video`，`POST /api/v1/services/aigc/video-generation/video-synthesis`（异步 task_id + 轮询） |
| 参数 | `prompt` / `media[]` / `resolution`(480P/720P/1080P) / `ratio` / `duration`(2-30) / `audio` / `prompt_extend` / `watermark` / `seed` / `wait`（`video_gen_server.py:481-493`） |
| 默认值 | `DEFAULT_RESOLUTION=480P`、`DEFAULT_DURATION=5`、`MIN_DURATION=2`、`MAX_DURATION=30`（`:34-49`） |
| 轮询 | 间隔 8s、上限 240s（`VIDEO_GEN_TIMEOUT_SECONDS`），超时返回 `timed_out` 并提示改用 `query_video_generation`（`:308-345`） |
| 输出 | **只有远程 URL**（`video_url`，约 24 小时有效），工具不落盘、不返回字节 |
| 凭据 | 优先取数据库 `ai_models`/`providers` 中名为 `wan3.0-video` 的行（`:348-380`），回退环境变量 `VIDEO_GEN_*`（`agent/config/config.py:62-64`） |

**关键事实：视频生成工具只给 URL，不负责落盘。**"把视频存到磁盘"这一步必须由别的东西完成——这正是当前所有问题的发源地。


**结论：桌面端不是"勉强可用"，而是"默认路径必然失败"。** 提示词依赖 shell（`mkdir` + `curl.exe` + 反斜杠路径），而「新建任务」页默认分类 `work` 映射到 `filesystem` 后端，`AgentBuilder.ts:23-25` 注释明确写着"仅文件读写（**没有 execute 工具**）"。只有用户手动切到「代码」分类，才可能走到 `LocalShellBackend`；即便如此，`curl.exe` 与 `\` 路径分隔符在 macOS/Linux 上同样不可用。

补充事实（后文问题清单会引用）：

- 桌面端**没有**等价于 Web `ExpertDirectiveMiddleware` 的请求级指令注入：`AgentManager.ts:126-127` 只装了 `createModelOverrideMiddleware`；`desktop/src` 全目录零引用 `PROMPT_VARIABLES`（`delivery_dir`/`asset_tool`/`platform_notes`）。
- 桌面端输入框里的委派提示词来自**渲染层本地硬编码模板**（`catalog.ts:182-185` 的"请先分析任务并拆分为子任务……"），因为服务端 `ExpertInfo.prompt_template` 恒为空串（`service.py:152`）。专家的业务上下文只存在于 subagent 的 system prompt 中（这条是通的）。
- 桌面端「视频生成」快捷 chip（`NewTaskPage.vue:443-450` 定义、`:624` 渲染）**没有任何 `@click`**，是死元素。
- 桌面端工作区里点开 mp4 显示「暂不支持预览」（`previewKind.ts:72-88`），因为 `previewKind.ts` 的 `IMAGE_EXTS` 与 `WorkspacePreviewServer.ts:14-36` 的 `MIME_TYPES` 都没有视频类型 —— 与"正文里能播"形成不一致。

#### 2.4.1 澄清：物化 / 回灌 / 预览 三者分工（与需求方描述的差异）

需求方描述为"物化存储 → 预览时再回灌到沙箱中显示"。核对代码后，实际分工如下（**这决定了本次方案的着力点**）：

| 环节 | 实际实现 | 与描述的差异 |
| --- | --- | --- |
| 物化 | `persist_artifact`（`artifacts.py:324-426`）把交付文件写入 `ArtifactStore`（本地磁盘或 MinIO），`status=ready` | 一致 |
| 回灌 | `ArtifactRestoreMiddleware.abefore_agent`（`artifact_restore.py:102-139`）在**每轮 agent 执行前**把"沙箱内缺失的历史产物"写回沙箱；**资源类产物（图片/音视频/压缩包）明确不回灌**（`:163-165`），交付目录由 `restore_delivery_artifacts` 回填宿主 staging（`:116`） | **回灌的目的不是预览**，而是"让后续轮次的 agent 仍能读写上一轮的产物"；视频被有意排除在外 |
| 预览 | `download` 接口（`agent_api.py:925-964`）**优先读持久副本**（`store.local_path` → `FileResponse`，否则 `_storage_response` 按 Range 返回），沙箱仅作兜底 | 预览**不经过沙箱**，回灌与预览没有依赖关系 |

**结论**：视频这条线**不依赖回灌**，真正缺的是三件事——① 让成片能可靠地落到（沙箱/宿主的）交付目录；② 让 `chat_artifacts` 用它正确的 MIME 登记；③ 让前端能把文档里的 `<video src=相对路径>` 解析成带鉴权的产物地址并播放。方案第 4 章的 D1/D4/D5 正是对应这三件事。

### 2.5 移动端现状

- 服务端已提供 `platform=mobile` 渲染分支与移动端运行环境说明（`agent/experts/platforms.py:22-27`）；
- 移动端工程已落地与 Web 同规则的纯函数工具（`MarkdownArtifacts.ets`、`ArtifactGroups.ets`、`ArtifactAssets.ets`），但**只有图片**：`sniffImageMime` 式解码、`ArtifactImage.ets` 渲染；
- `mobile/entry/src/main/ets` 全量检索无 video / mp4 相关代码。

### 2.6 两端差异对照

| 维度 | 桌面版 | Web 版 | 是否对称 |
| --- | --- | --- | --- |
| 专家来源 | 服务端同步（`platform=desktop`） | 服务端同一份 | ✅ |
| 提示词渲染 | 同步时渲染（模板无占位符 → 空操作） | 建图期渲染（同上，空操作） | ❌ 都享受不到渲染 |
| 落盘方式 | 模型执行 `mkdir` + `curl.exe`（**默认 `filesystem` 后端无 `execute`**，仅「代码」分类可用） | 模型执行 `curl.exe`（Linux 沙箱，不可用） | ❌ |
| 交付根 | 工作区根 `/` | `/artifacts/<thread>/turn-<n>/` | ❌ 语义不同（历史决策，见 D5 说明） |
| 素材工具 | `download_asset`（**仅图片**） | `download_asset`（**仅图片**） | ✅ 但都不支持视频 |
| 视频 MIME | `WorkspaceService.ts:80-82` 有视频白名单 | `artifacts.py:77-102` **无**视频类型 | ❌ |
| 视频预览 | 正文已实现（`markdown-videos.ts` + blob）；**文件列表/预览面板不支持** | **完全缺失** | ❌ |
| 回灌策略 | 不适用（本地工作区） | 视频列入资源类，不回灌 | ✅ |
| 打包 | `workspace:export-zip`（读工作区，含视频；自动带上同名目录） | `bundle.zip`（读 staging，含视频但可能已被清理） | ⚠️ |

### 2.7 与「文档写作专家」的关键对照（根因）

| 维度 | 文档写作专家 | 视频创作专家 |
| --- | --- | --- |
| 创建时间 | 2026-09-02 | 2026-09-06 |
| 提示词是否含占位符 | ✅ `{{platform_notes}}`（`service.py:891`）、`{{delivery_dir}}`（`:894`）、`{{asset_tool}}`（`:909`） | ❌ 零占位符（`:939-984`） |
| 提示词是否含平台命令 | ❌ 已清除 | ✅ `curl.exe` / PowerShell / `mkdir` / 反斜杠 |

## 4. 目标设计

### 4.1 设计原则（沿用并扩充）

> **专家只声明"做什么、交付什么"；平台负责"怎么落盘、怎么显示、怎么打包"。**

1. 专家定义（DB）中**不得出现**路径分隔符、shell 命令、平台目录约定；
2. 平台差异只能出现在**提示词渲染层**与**运行时适配层**；
3. 交付物必须是**显式登记 + 可枚举**的，不依赖对工具调用文本的猜测；
4. **（本次新增）长耗时媒体产物的落盘必须走"代理下载 + 显式登记 + 物化"通道，禁止让模型执行平台命令下载。** 视频 URL 有效性与沙箱网络策略都不受专家控制，只有代理下载能让两端行为一致。

### 4.2 分层契约

```
① 专家定义层（平台无关，存 experts 表）
   capabilities      : ["video.generate", "document.assemble"]
   prompt_template    : 只描述创作意图与交付物契约，含占位符变量
   deliverable_spec   : { root: "<title>.md",
                          resource_dir: "<title>/",
                          resource_patterns: { image: "figure-{n}.{ext}",
                                               video: "成片-{n}.{ext}" } }
                 │ 服务端按 platform 渲染（同步下发 or 请求期注入）
                 ▼
② 运行时适配层（每端一份实现）
   WorkspacePort     : 工作区读写（桌面=本地目录；Web=宿主 staging + 沙箱；移动端=服务端）
   DeliverablePort   : downloadAsset(url, relPath)  ← 图片与视频共用，按魔数分流
   PromptRenderer    : 注入 platform_notes / delivery_dir / asset_tool
                 │
                 ▼
③ 产物层（平台无关）
   Bundle = { thread_id, turn, root, resources[](图片+视频), manifest }
   预览 / 回灌 / 打包 / 展示 统一以 Bundle 为单位
```

### 4.3 交付物契约扩展（文档 + 同名资源目录）

保持"文档 `<标题>.md` + 与文档同名的资源目录 `<标题>/`"这一形态不变（两端已一致），仅把资源命名规则从"单一 pattern"扩展为"按类别分列"：

```jsonc
// packages/expert-contract/contract.json  （改动点）
"deliverable": {
  "root": "<title>.md",
  "resourceDir": "<title>/",
  "resourcePatterns": {                       // ← 由 "resourcePattern": "figure-{n}.{ext}" 改为分列
    "image": "figure-{n}.{ext}",
    "video": "成片-{n}.{ext}"
  },
  "webDeliveryRoot": "/artifacts/<thread_id>/turn-<n>"
}
```

说明：

- `resourcePatterns` 是**约定表达**，运行时不做强制校验（现状 `scan_delivery_artifacts` 收录交付目录内任意文件），因此本次改动**不引入兼容风险**，只需同步更新两侧契约测试的断言；
- 视频必须落在 `<交付目录前缀><标题>/成片-N.mp4`（带 `turn-<n>` 层），否则 `turn_from_path`（`delivery.py:63`）与前端 `parseBundleTurn` 解析不到轮次，产物无法按轮归属与打包。

### 4.4 决策 D1：素材工具统一通道（视频落盘的正解）

**把 `download_asset` 从"图片素材工具"升级为"素材工具"**，让视频复用图片已经跑通的整条流水线。

Web 侧（`web/backend`）：

| 文件 | 改动 |
| --- | --- |
| `src/core/storage/asset_fetcher.py` | 新增视频魔数识别（`ftyp` → mp4/mov/m4v、`EBML` → webm/mkv、`RIFF....AVI ` → avi）；`sniff_image_mime` 泛化为 `sniff_asset_mime`；`fetch_image` 泛化为 `fetch_asset`（保留旧名做别名，避免破坏既有调用与测试）；大小上限与超时按类型区分 |
| `src/api/agent/artifacts.py` | `ingest_remote_asset` 透传 asset 类型；`_MIME_BY_EXT` 补 `mp4/webm/mov/m4v/mkv/avi`（修 P0-6） |
| `src/agent/tools/artifact_assets.py` | 工具描述改为"把远程素材（图片/音视频）下载到交付目录"；返回结构保持 `{path,size,mime_type,artifact_id,persisted}` |

桌面侧（`desktop`）：

| 文件 | 改动 |
| --- | --- |
| `src/main/agent/tools/ArtifactAssetService.ts` | 魔数识别扩展至视频（与 Web 同规则）；单文件上限由固定 20MB 变为"图片 20MB / 视频 200MB"（与 `WorkspaceService.ts:80-82` 的媒体白名单上限对齐）；超时由 60s 提升至 300s（与 MCP 视频工具超时对齐） |
| `src/main/agent/tools/DesktopToolRegistry.ts` | `download_asset` 描述与 `url` 参数说明改为"素材（图片/音视频）"；返回结构对齐 Web（新增 `path`/`mime_type` 别名，保留 `relPath`/`mime` 兼容，修 P2-5） |

配套配置项（Web，`.env.example` 同步）：

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `ARTIFACT_FETCH_MAX_MB` | 100（已有） | 通用素材上限（沿用） |
| `ARTIFACT_FETCH_VIDEO_MAX_MB` | 200 | 视频单独上限，对齐桌面媒体白名单 |
| `ARTIFACT_FETCH_VIDEO_TIMEOUT_SECONDS` | 300 | 视频单独超时，对齐 MCP 视频工具 |

**这一条同时消掉了三个衍生问题**：

- P0-1 / P1-4 的根因（"必须切到代码分类才能用"）——专家不再依赖 `execute`，默认的 `filesystem` 后端即可完成落盘；
- P0-4 的根因（视频无落盘通道）——图片与视频共用同一条流水线；
- 跨平台问题——Windows/macOS/Linux 都用同一套工具调用，专家定义里不再出现任何平台命令。

### 4.5 决策 D2：提示词平台中立化

把 `service.py:924-985` 的 `system_prompt` 改写为**与文档写作专家同构**的平台无关模板：

- 删除：`if not exist ... mkdir`、`curl.exe`、PowerShell、反斜杠路径、`ls /<目录名>`、`cd 取物理路径`；
- 新增占位符：`{{platform_notes}}`（运行环境）、`{{asset_tool}}`（素材工具名）、`{{delivery_dir}}`（交付目录前缀，实际由【交付目录】一行在请求期注入，模板只声明"若任务中给出则以它为准，未给出则写工作区根目录"）；
- 落盘步骤改为调用素材工具。

改写要点（节选，完整版见实施清单）：


### 4.9 决策 D6：MCP 服务地址配置化

`api/mcp/service.py:289-291, 311-313` 的硬编码 `http://127.0.0.1:8001` 改为从配置读取（如 `MCP_PUBLIC_BASE_URL`，缺省回退 `http://127.0.0.1:<PORT>`），并在专家同步下发给桌面端时使用**客户端可访问**的地址。

## 5. 端到端时序（改造后）

### 5.1 Web 版一轮视频创作

```
用户：「+」→ 视频创作专家 → 输入创作要求 → 发送
  │
  ├─ 前端：body 带 expert_id / expert_name / platform=web
  ├─ 后端 _resolve_selection：注入【专家】；_prepare_delivery 算出 /artifacts/<thread>/turn-<n>/
  ├─ ExpertDirectiveMiddleware：注入平台说明 +【交付目录】块（含"文档与同名资源目录（配图/成片）"）
  ├─ 主 agent 委派「视频创作专家」subagent
  │    ├─ 调 MCP generate_video(prompt, duration=?, resolution=?, ratio=?, audio=?) → video_url
  │    ├─ 调 download_asset(url, "视频标题/成片-1.mp4")
  │    │     └─ 后端代理下载（视频魔数校验 / 200MB / 300s）
  │    │        → 写宿主 staging → 登记 chat_artifacts（mime=video/mp4）→ 持久化物化
  │    │        → SSE 推送 artifact 事件
  │    └─ 调 write_file("/artifacts/<thread>/turn-<n>/视频标题.md")（正文含 <video src="视频标题/成片-1.mp4">）
  ├─ 轮末：scan_delivery_artifacts 补登记遗漏文件 + 补全大小 + 推 artifact_updated
  └─ 前端：
       ├─ 消息气泡 / 右侧预览：<video src> 相对路径 → 产物虚拟路径 → 带鉴权拉字节 → blob → 播放
       ├─ 产物卡片：视频 + 文档分组展示，按 turn 归属
       └─ 打包下载：bundle.zip（本轮 / 整会话），含文档与成片目录结构
```

### 5.2 桌面版一轮视频创作

```
「新建任务」→「+」→ 视频创作专家 → 输入创作要求 → 发送
  │
  ├─ 默认分类 work → filesystem 后端（无 execute）即可，全程不依赖 shell
  ├─ 同步已就绪：/api/expert-sync/list?platform=desktop 下发平台化提示词（含 desktop 运行环境说明）
  ├─ 工具装配：document.assemble 能力 → 启用本地 download_asset；MCP → generate_video
  ├─ 主 agent 委派 subagent → generate_video → video_url
  ├─ download_asset(url, "视频标题/成片-1.mp4") → 主进程下载 → 原子写入工作区 → 返回 {path,size,mime_type}
  ├─ write_file("/视频标题.md")（正文含 <video src="视频标题/成片-1.mp4">）
  └─ 渲染层：extractWorkspaceVideoPaths → readWorkspaceMediaBytes → blob → 页面内播放
       └─ 打包：workspace:export-zip（工作区文件树 / 消息产物卡片入口）
```

## 9. 风险、兼容与回滚

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 视频体积导致浏览器端全量加载 | blob 方案必须先下完整个文件 | 内联上限（默认 100MB）+ 超限退化为"点击下载"；若后续需流式，评估一次性签名 URL |
| `download_asset` 语义扩大影响存量专家 | 文档写作专家也在用同一工具 | 泛化保持向后兼容（图片路径不变），仅新增类型分支；单测保留原有图片用例 |
| 大文件代理下载占用后端带宽/内存 | 200MB × 并发 | 流式落盘（不整体读入内存）优先实现；必要时加并发限制 |
| 提示词改写导致视频专家的产出风格漂移 | 模型对交付路径的理解改变 | 保留"时长/分辨率/画幅规划"全部原规则，仅改落盘与路径段落；端到端用例断言文档结构与成片命名 |
| MCP 服务地址配置化影响存量安装 | 桌面端可能缓存了旧的 MCP URL | 同步时更新 `experts.json`；保留 `127.0.0.1` 回退 |
| 存量库不补工具关联 | `seed_builtin_experts` 只更新字段 | 实施时增加 backfill（幂等） |
| 摘除 shell 依赖后行为变化 | 桌面端此前（切到「代码」分类时）可能已"能跑"，改造后走 `download_asset`，行为路径改变 | 端到端用例覆盖默认分类；保留原有图片路径不变，仅新增视频分支 |
| 回滚 | 提示词与工具映射均为配置级改动 | 回滚只需还原 `service.py` 的专家定义与 `capabilities`，无需数据迁移 |

### 11.2 与方案的实现调整

1. **不替换 `fetch_image`，而是新增 `fetch_asset`**：`fetch_image` 的现有调用点与单测语义（"非图片内容"直接拒绝）保持不变，统一入口以新函数承载，避免扩大改动面。
2. **图片上限在统一通道内单独保留**：用 `image_max_bytes` 参数区分，避免"统一按视频上限放宽"削弱图片原有约束（新增单测守住）。
3. **桌面端超时按目标扩展名预判档位**：下载前拿不到内容类型，而 `relPath` 由交付契约决定（`成片-N.mp4`），因此按扩展名选 60s / 300s。
4. **提示词不写字面命令名**：视频提示词若写"严禁使用 curl / PowerShell"，会命中平台中立性断言的禁用词表；改为"不要使用命令行、脚本或物理路径方式下载"，语义等价且提示词更干净。
5. **超出内联上限的成片也摘掉 `src`**（不只是加载中）：否则浏览器会去请求不存在的相对地址。这是前端单测断言先暴露、再修的行为。
6. **新增"最小成本档位"提示词规则**：用户明确要求"最小成本 / 最省额度 / 只做试片验证"时固定 `duration=2`、`resolution=480P`、`prompt_extend=false`，避免模型按内容自行放大（也让实测成本可预期）。

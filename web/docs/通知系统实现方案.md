# 通知系统实现方案

> 适用于 WorkMate Web 版，覆盖后端数据模型、API、事件驱动机制与前端交互全链路。

## 一、现状分析

TopBar.vue 中已有一个通知图标按钮，但目前只是一个空壳：

没有点击行为、没有未读计数、没有通知数据模型、没有后端 API。整个系统前后端均不存在任何通知相关实现。

## 二、可产生通知的业务场景

基于对系统实际功能的分析，以下业务模块存在天然的通知触发点：

| 业务模块 | 触发场景 | 来源代码 |
|---------|---------|---------|
| 知识库文档索引 | 文档索引完成 / 索引失败 | doc_service.py 的 ProgressObserver 观察者模式，状态变更为 indexed 或 failed 时 |
| 定时任务 | 任务执行成功 / 失败 / 状态异常 | cron_job.py，status 变为 error 或执行完成时 |
| Agent 运行 | 子 Agent 执行失败 | agent_api.py 的 SSE 流 agent_end 事件中 status=failed |
| 登录安全 | 异地登录 / 频繁登录失败 | login_record.py，连续失败时 |
| 系统管理 | RBAC 权限变更、用户被禁用等 | admin / rbac 相关 API |

## 三、方案设计

### 3.1 后端

#### 数据模型 - Notification 表

文件：web/backend/src/db/models/notification.py

字段说明：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | str (UUID) | 主键 |
| user_id | str (索引) | 接收者用户 ID |
| type | str | 通知类型: kb_indexed / kb_failed / cron_success / cron_failed / agent_error / security / system |
| title | str | 通知标题 |
| content | str | 通知正文 |
| level | str | info / success / warning / error |
| link | str (nullable) | 点击跳转路由，如 /knowledge-base?kb_id=xxx |
| metadata | JSON | 扩展字段 (业务 ID 等) |
| is_read | bool | 是否已读 |
| created_at | datetime | 创建时间 |
| read_at | datetime (nullable) | 已读时间 |

注册到 web/backend/src/db/models/__init__.py 的导出列表中。

#### 通知服务模块

目录结构：

- web/backend/src/api/notification/__init__.py - router 导出
- web/backend/src/api/notification/notification_api.py - REST 接口
- web/backend/src/api/notification/service.py - 业务逻辑 + 通知分发
- web/backend/src/api/notification/schemas.py - Pydantic 模型

REST API 端点（遵循系统现有的 /api 前缀 + @handle_errors + ok() 响应格式）：

| 方法 | 路径 | 功能 |
|------|------|------|
| GET | /api/notifications | 获取通知列表（分页，支持 type / is_read 筛选） |
| GET | /api/notifications/unread_count | 获取未读数量（轮询用，轻量） |
| PATCH | /api/notifications/{id}/read | 标记单条已读 |
| POST | /api/notifications/read_all | 全部标记已读 |
| DELETE | /api/notifications/{id} | 删除单条通知 |

#### 通知触发机制 - 事件驱动

采用轻量级事件总线模式，不侵入现有业务代码。

核心类 NotificationBus（文件：web/backend/src/core/notification_bus.py）：

- subscribe(handler)：注册通知处理器
- publish(event)：发布通知事件，异步执行所有已注册的处理器

各业务模块在关键节点调用 NotificationBus.publish()：

- 知识库：在 DatabaseProgressObserver.on_progress() 中，当 ctx.status 变为 indexed 或 failed 时发布事件
- 定时任务：在任务执行完成回调中发布事件（目前定时任务是前端 Mock，后端化后接入）
- Agent 流：在 chat_stream 的 agent_end 事件中，status 为 failed 时发布事件
- 登录安全：在登录失败计数达到阈值时发布事件

NotificationBus 的 handler 负责：写入 DB，如果用户在线则通过 SSE 推送。

#### 实时推送 - SSE 端点

系统已有成熟的 SSE 实现模式（agent_api.py 的 chat_stream），通知推送复用相同模式：

- GET /api/notifications/stream - SSE 长连接
- 用户登录后建立连接，服务端维护 user_id 到 asyncio.Queue 的映射
- 新通知到达时向对应用户的 Queue 投递，SSE 推送
- 支持心跳保活（每 30s 发 ping）

### 3.2 前端

#### 通知 Store - stores/notification.ts

Pinia store 管理通知状态：

- notifications: Ref<Notification[]> - 通知列表
- unreadCount: Ref<number> - 未读计数
- sseConnection: EventSource | null - SSE 连接
- actions: fetchList / fetchUnreadCount / markRead / markAllRead / delete / connectSSE / disconnectSSE

#### 通知 API - services/notificationApi.ts

遵循系统现有的 services/request.ts axios 封装模式，调用上述 REST 端点。

#### TopBar 改造

将 web/frontend/src/components/TopBar.vue 中的空壳通知按钮替换为带 Popover 的通知组件：

- 使用 el-popover 包裹 Bell 图标按钮
- 未读数大于 0 时显示 badge 角标（超过 99 显示 99+）
- Popover 内容区渲染 NotificationPanel 组件

#### 通知面板组件 - components/NotificationPanel.vue

面板布局示意：

- 顶部：标题「通知」+ 「全部已读」按钮
- 中间：通知列表，每条包含类型圆点、标题、内容摘要、时间、查看链接
- 底部：「查看全部通知」链接

特性：

- 按时间倒序展示最近 20 条
- 不同 level 用不同颜色圆点区分（success 绿色、error 红色、warning 黄色、info 蓝色）
- 点击通知项标记已读并跳转至 link 路由
- 未读通知有高亮背景
- 底部「查看全部通知」跳转至独立通知列表页（可选）

#### SSE 连接生命周期

- 在 web/frontend/src/components/MainLayout.vue 的 onMounted 中调用 notificationStore.connectSSE()
- 在 onUnmounted 中调用 disconnectSSE()
- 用户登出时（web/frontend/src/stores/auth.ts 的 clearTokens()）断开连接
- SSE 收到通知时：更新 unreadCount + 使用 ElNotification 弹出桌面通知

#### 未读计数轮询兜底

SSE 连接可能因网络中断而断开，需要一个降级轮询：

- 每 60 秒调用一次 GET /api/notifications/unread_count
- SSE 断开时自动切换为 30 秒轮询
- SSE 重连成功后恢复

### 3.3 通知类型清单

| type | level | title 示例 | content 示例 | link |
|------|-------|-----------|-------------|------|
| kb_indexed | success | 文档索引完成 | 《产品手册.pdf》已成功索引 | /knowledge-base?kb_id=xxx |
| kb_failed | error | 文档索引失败 | 《数据.xlsx》索引失败：权限不足 | /knowledge-base?kb_id=xxx |
| cron_success | info | 定时任务执行完成 | 「数据同步」执行成功，耗时 48s | /scheduled-tasks |
| cron_failed | error | 定时任务执行失败 | 「日志清理」执行失败：权限不足 | /scheduled-tasks |
| agent_error | warning | 子 Agent 执行异常 | 子 Agent「分析助手」执行失败 | /chat?thread_id=xxx |
| security | warning | 异地登录提醒 | 您的账号在 IP 1.2.3.4 登录 | - |
| system | info | 系统通知 | 欢迎使用 WorkMate | - |

## 四、实施步骤

### 4.1 后端

1. 创建 Notification 数据模型，注册到 db/models/__init__.py
2. 创建 api/notification/ 模块（service + api + schemas）
3. 注册路由到 api/__init__.py

5. 在知识库 ProgressObserver 中接入事件发布（改造成本最低，已有 Observer 模式）
6. 实现 SSE 端点 /api/notifications/stream

### 4.2 前端

1. 创建 types/notification.ts
2. 创建 services/notificationApi.ts
3. 创建 stores/notification.ts（含 SSE 连接管理）
4. 创建 components/NotificationPanel.vue
5. 改造 components/TopBar.vue
6. 在 components/MainLayout.vue 接入 SSE 生命周期

### 4.3 逐步接入通知源

1. 知识库文档索引（已有 Observer 模式，改造成本最低）
2. 定时任务（需先将前端 Mock 后端化）
3. Agent 异常
4. 安全通知

## 五、技术决策说明

- SSE 而非 WebSocket：系统已在聊天流中验证了 SSE 的可靠性（StreamingResponse + 前端 fetch ReadableStream），通知推送是单向服务端到客户端，SSE 完全够用且实现成本更低。
- 事件总线而非直接写库：将通知生产与消费解耦，业务代码只需 publish，不关心通知如何存储和推送。
- 轮询兜底：SSE 在弱网环境可能断开，未读计数轮询确保用户始终能看到通知红点。
- 无独立通知列表页（一期）：先通过 Popover 面板满足需求，后续如果通知量大再增加独立页面。

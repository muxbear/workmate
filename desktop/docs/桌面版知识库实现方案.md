# 桌面版知识库实现方案

## 一、需求概述

设置窗口「知识库设置」标签页已完成 UI 与配置持久化：18 个 `knowledge.*` 配置项写入 `src/main/settings/schema.ts`，可读写、可持久化、目录可选。但这些配置目前**没有任何代码消费**——全部 `applyTiming: 'pending'`（仅持久化）。

与此同时，主页面「知识库」（`KnowledgePage.vue`，1987 行）是纯 mock：`KNOWLEDGE_GROUPS` / `KNOWLEDGE_FILES` 硬编码，零 `window.api` 调用，上传的 `File` 字节被直接丢弃，`ask()` 只是字符串模板拼接。

本方案的目标是让这 18 项配置**真正生效**：建成一条本地优先的 RAG 引擎（导入 → 解析 → 切片 → 索引 → 检索 → 问答 → 图谱抽取），并把 `KnowledgePage` 从 mock 接到真实数据。

**三项已确认的决策**：

1. **先稀疏检索、向量后置**：以 SQLite FTS5 + `bm25(k1, b)` 为主链路，embedding / rerank 做成可插拔接口；未配置 embedding 时自动降级为纯稀疏，功能完整可用。
2. **覆盖全量**，含知识图谱抽取。
3. 本地优先，不引入外部服务依赖。

### 2.2 必须绕开的两个坑

- **截断上限**：`FileLoaders.ts` 的 `MAX_TEXT_CHARS = 200KB` / `MAX_BINARY_BYTES = 20MB` 是**模块级常量**，超出静默截断。需改造为可选参数（默认值不变，避免影响既有预览/附件链路），并把 `truncated` 落库提示用户。
- **代理不生效**：`src/main/index.ts:348` 的代理只作用于 Electron session，**axios 不走代理**。新增的 embedding / rerank HTTP 调用须显式读取 `network.proxyMode` / `proxyUrl` 构造代理，否则用户开启的代理对知识库无效。

## 三、与 Web 版 RAG 的对齐

`web/backend/src/api/knowledge_base/` + `core/rag/` **已有一套完整实现**，其 `IndexConfigSchema`（`schemas.py:9-25`）与桌面这 18 项设置几乎 1:1 对应。仓库已有《桌面版与WEB版对接方案.md》，对齐命名可让后续互通退化为纯列映射。

| 维度 | Web 版 | 桌面版现状 | 本方案取舍 |
|------|--------|-----------|-----------|
| 配置承载 | 每知识库一份 `config`（JSON `IndexConfig`）+ 每文档可覆盖 | 全局 `knowledge.*` 设置 | **保留全局**（与已建成设置页一致）；同时在**每个文档行快照生效配置**，保证重索引可复现 |
| 表名 | `knowledge_bases` / `knowledge_base_documents` / `knowledge_base_entities` / `knowledge_base_relations` | 无 | **沿用 web 表名**；桌面额外需要 `knowledge_base_chunks`（web 把分块放在 Milvus/Chroma，桌面无向量库） |
| 状态机 | `queued→parsing→chunking→embedding→bm25→extracting→indexed`，进度 0/3/15/30/55/70/100，失败 `failed` | 无 | **完全沿用**，含进度百分比 |
| 稀疏检索 | 名为 BM25，实为客户端 TF 计数；`bm25_k1`/`bm25_b` **从未被读取** | 无 | 桌面用 **FTS5 真 BM25**，两项配置首次真正生效 |
| 向量库 | Milvus / Chroma | 无 | 桌面**不引向量库**：`embedding` 存 BLOB + JS 暴力余弦 |
| 融合 | RRF，`RRF_K=60`，**不加权**；`alpha` 只影响展示分 | 无 | 沿用 `RRF_K=60`，但让 `hybridWeight` 真正参与加权 |
| 重排 | **未实现**（仅 schema 字段） | 无 | 桌面**首次落地** |
| 图谱抽取 | LangExtract + 中文 few-shot 提示词；实体类型：人物/组织/概念/产品/地点/时间/模型/算法/框架/技术 | 无 | **复用同一套实体类型与提示词思路**（提示词移植为 TS 常量） |
| Agent 工具 | `agent/tools/kb_search.py`（`kb_search` + `list_knowledge_bases`） | 无 | 对齐为同名 `kb_search` 工具 |
| 分块单位 | 界面标 "tokens"，实际是**字符**（`token_count = len(text)//2`） | 无 | 桌面用真实 token 估算，比 web 准确 |

**结论**：桌面版是"本地优先版"的 web RAG——语义与命名对齐 web，实现换成 SQLite/FTS5，并在 BM25 真实性、重排、token 计量三处优于 web。

## 四、目标目录结构

索引库跟随 `knowledge.directory`（与设置页文案"原始文件、解析缓存与向量索引的存放位置"一致；换目录即换一套知识库，旧库不迁移）：

```
<knowledge.directory>/                 # 默认 ~/KeWork/knowledge-base
├── index.db                           # SQLite：库/文档/分块/向量/图谱 + FTS5
├── index.db-wal  index.db-shm
└── files/<kbId>/<docId>/<filename>    # 原始文件副本（导入时复制，源文件可删）
```

## 五、分层实现方案

### 1. 主进程：`src/main/knowledge/KnowledgeStore.ts`（新）

打开 `index.db` 并执行自管迁移。**不并入 `ke-work.db`**：知识库是可重定位的独立存储，且分块/向量 blob 会显著撑大主库（主库还承载 LangGraph checkpoint）。

- `open(dir)`：`better-sqlite3` + `pragma('journal_mode = WAL')` + `foreign_keys = ON`；以 `kb_meta.schema_version` 作为版本号，内置迁移数组按版本递增执行（复刻 `src/main/database/local/migrations.ts` 的写法，独立版本序列）
- `close()`：切换 `knowledge.directory` 时关旧库、开新库
- 仓储方法：库/文档 CRUD、`insertChunks` / `deleteChunksByFile`、`searchSparse` / `searchDense`、图谱读写

**表结构（名称对齐 web）**

```sql
knowledge_bases(id, user_id, name, description, scope, status,
                config JSON,           -- 建库时的生效配置快照
                docs_count, chunks_count, entities_count, relations_count,
                size_bytes, created_at, updated_at)

knowledge_base_documents(id, kb_id, user_id, name, type, size_bytes,
                content_hash,          -- sha256，同库去重
                storage_path, status, progress, error_message,
                chunks_count, entities_count, relations_count,
                char_count, truncated, config JSON,   -- 生效配置快照
                uploaded_at, indexed_at)

knowledge_base_chunks(id, doc_id, kb_id, chunk_index, content,
                token_count, doc_name, doc_type, heading,
                embedding BLOB, embedded_at)          -- 无 provider 时为 NULL

knowledge_base_entities(id, kb_id, doc_id, name, type, mentions, source_text)
knowledge_base_relations(id, kb_id, doc_id, from_entity, to_entity, label, weight,
                source_entity_id, target_entity_id, chunk_id)

kb_chunk_fts USING fts5(text_tokens, content='', tokenize='unicode61')
kb_meta(key, value)
```

**中文分词（关键设计）**：FTS5 的 `unicode61` 不做中文切词，整句会退化成一个 token。方案是写入前用 Electron 内置的 `Intl.Segmenter('zh', {granularity:'word'})` 分词、空格拼接后存入 `kb_chunk_fts.text_tokens`（contentless 表，rowid 对齐 `knowledge_base_chunks`），查询串同样先分词。

**零新增依赖**，已在 Node v24 实测：

```
知识库的向量检索与重排策略
  → 知识 | 库 | 的 | 向量 | 检索 | 与 | 重排 | 策略
```

优于引入 nodejieba（原生依赖）或改用 FTS5 trigram（召回质量差）。

### 2. 主进程：`src/main/knowledge/ChunkingService.ts`（新）

`split(text, opts) → Chunk[]`，按 `chunkStrategy` 分派（策略名与 web `splitters.py` 一致，桌面实现四种）：

| 策略 | 实现 |
|------|------|
| `recursive` | `RecursiveCharacterTextSplitter`，分隔符 `["\n\n","\n","。","."," ",""]`（对齐 web） |
| `markdown` | `MarkdownTextSplitter`，标题路径写入 `chunk.heading` |
| `fixed` | 定长窗口 + `chunkOverlap` |
| `semantic` | 句切分后计算相邻句 embedding 相似度，在低相似处断开；**无 embedding provider 时降级为 `recursive`** |

需新增依赖 `@langchain/textsplitters`（`@langchain/core` v1 已移除 `TextSplitter`，当前未安装）。

### 3. 主进程：`src/main/knowledge/IngestionPipeline.ts`（新）

单文档状态机，**阶段与进度完全沿用 web**：

```
queued(0) → parsing(3) → chunking(15) → embedding(30) → bm25(55)
          → extracting(70) → indexed(100)
                              ↘ failed(-1) / canceled
```

每步落库（`status` / `progress`）并推送 `knowledge:import-progress` 事件。

- **`maxUploadSize`**：`stat().size` 超限直接置 `failed`，不进入解析
- **`maxFilesPerBatch`**：在 IPC handler 层截断本次请求
- **`uploadTimeout`**：每个文档整段处理用 `Promise.race` 超时兜底，超时中止并记 `failed`
- **`graphEnabled`**：为真时才进入 `extracting` 阶段（与 web 一致：图谱失败不影响文档 `indexed`）
- 导入时把源文件复制进 `files/<kbId>/<docId>/<filename>`；sha256 命中同库已有哈希则复用，不重复建索引
- 无 embedding provider 时跳过 `embedding` 阶段（`chunking → bm25`），`chunk.embedding` 留 NULL

### 4. 主进程：`src/main/knowledge/EmbeddingProvider.ts`（新）

继承 `@langchain/core/embeddings` 的抽象 `Embeddings`，实现 `embedDocuments` / `embedQuery`：

- `resolve(embeddingModel)`：经 `ModelService.getCredential(id)` 取 `{url, apiKey}`，POST `{baseUrl}/embeddings`（OpenAI 兼容），复用 `ImageGenerationService.ts:18` 的 axios 直连写法 + 2.2 节的显式代理处理
- `available()`：无凭据或调用失败返回 false → 检索层自动纯稀疏
- 维度校验：返回向量长度与 `vectorDimensions` 不符时报明确错误，避免静默写坏索引

### 5. 主进程：`src/main/knowledge/RetrievalService.ts`（新）

```ts
retrieve({ kbId, query, topK?, mode? }) → { hits: Hit[], rerankSkipped: boolean }
```

1. **稀疏**（`sparseRetrieval` 为真）：查询串分词后 `kb_chunk_fts MATCH`，`ORDER BY bm25(kb_chunk_fts, :k1, :b)` —— **`bm25K1` / `bm25B` 直接作为 FTS5 `bm25()` 辅助函数的实参**，是设置项与引擎最直接的一处对应
2. **稠密**（`EmbeddingProvider.available()` 为真）：查询向量化，取该库 `embedding IS NOT NULL` 的分块做 JS 内暴力余弦。本地量级（万级分块 × 1024 维 ≈ 40 MB）单次扫描在几十毫秒内，**不引 sqlite-vec 等原生扩展**，规避 Electron 跨平台打包负担
3. **融合**：两路各取 `topK` 候选，RRF（`RRF_K = 60`，对齐 web）加权版：`score = w/(60+rank_dense) + (1-w)/(60+rank_sparse)`，`w = hybridWeight`
4. **重排**（`rerankEnabled`）：POST OpenAI 兼容 `/rerank`；**未配置端点时为 no-op**，返回 `rerankSkipped: true` 供 UI 提示
5. 末段按 `topK` 截断，回带 `{chunkId, docId, docName, chunkIndex, content, score, vecScore, bm25Score}`（字段名对齐 web `search_api.py` 的 results）

### 6. 主进程：`src/main/knowledge/GraphExtractor.ts`（新）

`graphEnabled` 为真时按块抽取：聊天模型取 `graphModel`（经 `ModelService.getCredential`，回退默认模型），结构化输出：

```json
{
  "entities":  [{ "name": "…", "type": "…", "source_text": "…" }],
  "relations": [{ "from": "…", "to": "…", "label": "…", "weight": 1.0 }]
}
```

**实体类型与提示词移植 web `graph_service.py`**（人物/组织/概念/产品/地点/时间/模型/算法/框架/技术）。写入 `knowledge_base_entities` / `knowledge_base_relations`，按 `(kb_id, doc_id, name)` 去重（对齐 web `_persist`）。检索侧提供 `expandByGraph(seedEntities, hops = 1)` 做一跳关联召回，与主结果合并去重。

### 7. 主进程：`src/main/knowledge/KnowledgeService.ts`（新，门面）

装配 `KnowledgeStore` + `IngestionPipeline` + `RetrievalService` + `GraphExtractor`，持有 `SettingsStore` 引用，**18 项配置的读取集中于此**（见第六节对照表）。对外暴露：库/文档 CRUD、`import()`、`reindex()`、`search()`、`ask()`、`stats()`。

`ask()`：检索 → 组装带引用上下文 → 复用现有聊天模型流式输出（同 `agent:stream-*` 做法推事件）。

### 8. 主进程：`src/main/ipc/knowledge-handlers.ts`（新）

沿用 `registerConfigHandlers` 的 `ok()` / `fail()` 包装；因知识库是**用户级**数据，须加 `session.requireUserId()` 守卫（与机器级 `config:*` 不同）。

| 通道 | 说明 |
|------|------|
| `knowledge:list-kbs` / `create-kb` / `update-kb` / `delete-kb` | 库 CRUD（对齐 web `/api/knowledge-bases`） |
| `knowledge:list-docs` / `remove-doc` / `retry-doc` | 文档操作（对齐 web `doc_api.py`，`retry` 仅允许 `failed`） |
| `knowledge:import` | 入参 `{kbId, filePaths[]}`，按 `maxFilesPerBatch` 截断，返回 `docIds`；进度走事件 |
| `knowledge:search` | 检索，`{mode, topK}` 可选，返回命中片段 |
| `knowledge:ask` / `knowledge:cancel-ask` | 流式问答 |
| `knowledge:stats` | 文件数 / 分块数 / 占用（复用 `computeDirSize`） |
| `knowledge:graph` | 实体/关系查询与一跳展开 |
| 事件：`knowledge:import-progress`、`knowledge:ask-chunk`、`knowledge:ask-done` | 主进程 → 渲染层 |

### 9. Preload 桥接

`src/preload/index.ts` + `index.d.ts` 新增 `KnowledgeAPI`（方法 + 事件订阅返回 `off` 函数，对齐既有 `onRuntimeProgress` 写法）。

## 六、配置项消费对照表（18 项）

|--------|------|--------|---------|---------|

| `knowledge.chunkStrategy` | `semantic` | `ChunkingService.split()` | 四策略分派；semantic 无 embedding 时降级 recursive | `chunk_strategy`（web 默认 recursive） |

| `knowledge.bm25K1` | 1.5 | FTS5 SQL | `bm25(kb_chunk_fts, :k1, :b)` 实参 | `bm25_k1`（**web 未使用**） |
| `knowledge.bm25B` | 0.75 | FTS5 SQL | 同上 | `bm25_b`（**web 未使用**） |

## 八、关键设计决策

1. **索引库随 `knowledge.directory` 走**，不并入 `ke-work.db`：知识库是可重定位的独立存储，且分块/向量 blob 会撑大主库（主库还承载 LangGraph checkpoint）。

2. **不引向量库 / 原生扩展**：`embedding` 存 BLOB（`Float32Array`），检索时 JS 内暴力余弦。本地量级下延迟可接受，避免 sqlite-vec / FAISS 的 Electron 跨平台打包负担。后续若分块数超十万级，再评估 `loadExtension` 引入 sqlite-vec。

3. **RRF 加权而非分数加权求和**：BM25 分数量纲无界、与余弦 [-1,1] 不可比，min-max 归一小候选集下不稳定。沿用 web 的 `RRF_K = 60`，但让 `hybridWeight` 真正参与加权（web 的 alpha 只影响展示分，属设置虚设）。

4. **`Intl.Segmenter` 做中文分词**：零依赖、Electron 内置，配合 FTS5 `unicode61` 使用。

5. **`chunkSize`/`chunkOverlap` 以 token 计**：用轻量估算器（CJK 字符计 1，其余 `ceil(len/4)`）封装在 `estimateTokens()` 单点，后续可无痛替换为 `js-tiktoken`。

6. **表名与状态机对齐 web**：`knowledge_bases` 系列表名、7 阶段状态机与进度百分比全部沿用 web，使后续桌面↔WEB 对接退化为纯列映射；桌面额外多一张 `knowledge_base_chunks`（web 的分块在向量库里）。

7. **配置全局、快照落库**：桌面保持全局 `knowledge.*`（与已建成设置页一致），但在每个文档行记录生效配置快照，保证"重索引可复现"——等效 web 的每库/每文档配置覆盖能力。

8. **图谱抽取失败不阻断索引**：与 web 一致，`extracting` 阶段异常只记日志，文档仍进 `indexed`。

9. **降级对用户可见**：embedding / rerank 未配置时不静默失效，检索结果带 `rerankSkipped` 标记，设置页显示"向量检索未启用"提示。

## 一、背景与目标

### 1.1 页面定位

知识库是桌面版「本地优先」能力的重要落点：用户把工作资料（PDF／Word／Excel／PPT／Markdown／TXT）导入知识库，
系统按配置建立索引（切片 → 向量化 → BM25 倒排 → 实体／关系抽取），随后既能被用户在大页面里直接提问，
也能被 Agent 会话检索调用。

### 1.2 本方案目标

1. 完整梳理知识库页面的**全部功能点**（共 42 项，见第三、四章）；
2. 对照现有前端实现，逐点给出**基于当前技术栈的落地方案**（见第十二章）；
3. 明确数据层、索引层、检索层、配置层的**改动清单与阶段划分**（见第十四、十五章）。

### 1.3 必须遵守的既有约束（desktop/AGENTS.md）

| 约束 | 对知识库的直接影响 |
| --- | --- |
| 严格三层：renderer → preload → main，主进程是权威 | 文件字节、路径、索引任务全在主进程；渲染层只传 ID 与相对路径 |
| 渲染层不传路径或权限 | 上传必须由主进程落盘，渲染层不能直接把绝对路径交给业务层 |
| Repository 策略模式 + `DataSourceFactory` 按工作模式注入 | 知识库需定义 `IKnowledgeRepository`，本地走 SQLite、云端走 HTTP |
| 受保护 IPC 走 `session.requireUserId()` | 所有知识库 IPC 必须按登录用户隔离（现有 `knowledge:*` 已如此） |
| 注释／文档以中文为主 | 新增代码注释、文档、提交信息用中文 |

## 四、功能点逐一分析（改造前基线）

> 本章逐点记录改造前的交互与代码依据，作为实现与回归对照的基线；改造后的落地情况见 18.4。

### 4.1 布局与导航（KP-01 ~ KP-06）

| 功能点 | 交互与行为 | 代码实现要点 | 缺口 |
| --- | --- | --- | --- |
| KP-01 入口 | 点击左侧「知识库」切换到知识库页 | `Home.vue` 用 `activeNav` 单值切换视图，`<KnowledgePage key="knowledge" />` 每次进入都是新实例（状态不保留） | 切换回来会丢失已打开的标签页、滚动位置 |
| KP-02 三栏工作台 | 分组栏 / 文件区 / 右侧面板 | `.kb-workbench` 用 flex + `--panel-collapsed`、`--panel-full` 两个修饰类控制三种形态 | 无 |

| KP-06 全屏/还原 | 全屏时 `--panel-full` 让面板占满工作台；Esc 退出全屏 | `togglePanelFullscreen()` 全屏必然先展开；`onDocumentKeydown` 里 Esc 时同时清 `panelFullscreen` 与 `panelCollapsed` | 无 |

### 5.1 差距总览

### 5.2 关键结论（对实现方案的影响）

1. **渲染层骨架可直接复用**：`knowledgeTree.ts`、`knowledgeList.ts`、`uploadIndex.ts`、`knowledgeFields.ts` 都是与数据源无关的纯函数，官方注释也已写明「等知识库引擎落地后可原样复用」。实现方案应尽量不动这些文件，只替换数据来源。
2. **配置链路已经打通**，索引管线应把它当作唯一配置入口：`全局值 ← 按库覆盖` = 生效配置（`KnowledgeSettingsService.getEffective()`）；上传时再把生效配置里的 14 个索引项作为**文档级配置快照**随文件落库。
3. **上传必须换掉现有取字节方式**：渲染层的 `File` 对象在 Electron 里拿不到真实路径（`File.path` 已在 Electron 32+ 移除），项目已经暴露了 `window.api.getPathForFile(file)`（内部用 `webUtils.getPathForFile`），`PlusMenu.vue` 与 `NewTaskPage.vue` 已在用。上传链路应统一走这条路径：**渲染层只把「文件绝对路径 + 相对目录结构」交给主进程，主进程负责复制落盘**。
4. **分组语义可映射到数据字段**：`local / shared / cloud` 三种分组恰好对应「本地创建、他人共享给我、云端知识库」三类来源，建议落成 `kind` 字段而不是三张表。
5. **索引进度需要流式 IPC**：项目已有成熟模式（`agent:send` → `agent:stream-*` 事件 + 按窗口 id 管理 `AbortController`），索引任务应沿用同一套「开始/进度/完成/失败/取消」事件模型。
6. **与后端的配置口径必须对齐**（见 5.3），否则云端模式下同一份配置两边解释不一致。

### 5.3 与 `web/backend` 的配置口径差异（必须先解决）

后端 `api/knowledge_base/schemas.py::IndexConfigSchema` 与桌面 17 项配置并非一一对应：

| 桌面（短 key） | 取值/区间（桌面） | 后端字段 | 差异与建议 |
| --- | --- | --- | --- |
| `chunkStrategy` | semantic / fixed / markdown / recursive | `chunk_strategy` | 后端多一个 `agentic`；建议桌面补上或后端收敛 |
| `chunkSize` | 100~8192，默认 800 | `chunk_size` | **区间冲突**：后端 128~2048，默认 512 → 需统一 |
| `chunkOverlap` | 0~4096，默认 120 | `chunk_overlap` | **区间冲突**：后端 0~512，默认 64 → 需统一 |
| `embeddingModel` | text-embedding-3-large / bge-m3 / 自定义 | `embedding_model` | 默认值不同（`text-embedding-v4`），需统一 |
| `vectorDimensions` | 1024 / 1536 / 3072 | `embedding_dim` | 语义一致，建议后端也用枚举校验 |
| `sparseRetrieval`（布尔） | 开关 | `sparse_algo`（bm25/bm25_plus/tf_idf/none） | **语义不同**：建议桌面把布尔改为算法的 `none` 分支，或后端接受布尔 |
| `bm25K1` | 0~10，默认 1.5 | `bm25_k1` | 一致 |
| `bm25B` | 0~1，默认 0.75 | `bm25_b` | 一致 |
| `hybridWeight` | 0~1，默认 0.65 | `hybrid_alpha` | 语义一致（向量权重），建议改名对齐 |
| `rerankEnabled` | 布尔，默认 true | `enable_reranker`，默认 false | 默认值冲突 → 需统一 |
| `rerankModel` | 枚举 + 自定义 | `reranker_model` | 一致 |
| `topK` | 1~100，默认 12 | `top_k` | **区间冲突**：后端 1~50 → 需统一 |

| `directory` | 本地存储目录 | 无 | 机器级配置，仅本地模式有意义 |

> 建议：以「桌面配置项」为主定义一份**共享契约**（表格形式写进对接文档），后端把 `IndexConfigSchema` 的区间/默认值/字段名对齐；`graphModel` 拆成 `entityModel` + `relationModel` 两个可选项更贴近后端实现。

## 六、需求概述与已确认的决策

> 说明：本章及第十章的代码行号来自 v1 评审时（`KnowledgePage.vue` 为 1987 行）；当前页面已增至 3287 行，配置项与章节结论仍然成立。

设置窗口「知识库设置」标签页已完成 UI 与配置持久化：18 个 `knowledge.*` 配置项写入 `src/main/settings/schema.ts`，可读写、可持久化、目录可选。但这些配置目前**没有任何代码消费**——全部 `applyTiming: 'pending'`（仅持久化）。

与此同时，主页面「知识库」（`KnowledgePage.vue`，1987 行）是纯 mock：`KNOWLEDGE_GROUPS` / `KNOWLEDGE_FILES` 硬编码，零 `window.api` 调用，上传的 `File` 字节被直接丢弃，`ask()` 只是字符串模板拼接。

本方案的目标是让这 18 项配置**真正生效**：建成一条本地优先的 RAG 引擎（导入 → 解析 → 切片 → 索引 → 检索 → 问答 → 图谱抽取），并把 `KnowledgePage` 从 mock 接到真实数据。

**三项已确认的决策**：

1. **先稀疏检索、向量后置**：以 SQLite FTS5 + `bm25(k1, b)` 为主链路，embedding / rerank 做成可插拔接口；未配置 embedding 时自动降级为纯稀疏，功能完整可用。
2. **覆盖全量**，含知识图谱抽取。
3. 本地优先，不引入外部服务依赖。

## 八、与 Web 版 RAG 的对齐

`web/backend/src/api/knowledge_base/` + `core/rag/` **已有一套完整实现**，其 `IndexConfigSchema`（`schemas.py:9-25`）与桌面这 18 项设置几乎 1:1 对应。仓库已有《桌面版与WEB版对接方案.md》，对齐命名可让后续互通退化为纯列映射。

| 维度 | Web 版 | 桌面版现状 | 本方案取舍 |
|------|--------|-----------|-----------|
| 配置承载 | 每知识库一份 `config`（JSON `IndexConfig`）+ 每文档可覆盖 | 全局 `knowledge.*` 设置 | **保留全局**（与已建成设置页一致）；同时在**每个文档行快照生效配置**，保证重索引可复现 |
| 表名 | `knowledge_bases` / `knowledge_base_documents` / `knowledge_base_entities` / `knowledge_base_relations` | 无 | **沿用 web 表名**；桌面额外需要 `knowledge_base_chunks`（web 把分块放在 Milvus/Chroma，桌面无向量库） |
| 状态机 | `queued→parsing→chunking→embedding→bm25→extracting→indexed`，进度 0/3/15/30/55/70/100，失败 `failed` | 无 | **完全沿用**，含进度百分比 |
| 稀疏检索 | 名为 BM25，实为客户端 TF 计数；`bm25_k1`/`bm25_b` **从未被读取** | 无 | 桌面用 **FTS5 真 BM25**，两项配置首次真正生效 |
| 向量库 | Milvus / Chroma | 无 | 桌面**不引向量库**：`embedding` 存 BLOB + JS 暴力余弦 |
| 融合 | RRF，`RRF_K=60`，**不加权**；`alpha` 只影响展示分 | 无 | 沿用 `RRF_K=60`，但让 `hybridWeight` 真正参与加权 |
| 重排 | **未实现**（仅 schema 字段） | 无 | 桌面**首次落地** |
| 图谱抽取 | LangExtract + 中文 few-shot 提示词；实体类型：人物/组织/概念/产品/地点/时间/模型/算法/框架/技术 | 无 | **复用同一套实体类型与提示词思路**（提示词移植为 TS 常量） |
| Agent 工具 | `agent/tools/kb_search.py`（`kb_search` + `list_knowledge_bases`） | 无 | 对齐为同名 `kb_search` 工具 |
| 分块单位 | 界面标 "tokens"，实际是**字符**（`token_count = len(text)//2`） | 无 | 桌面用真实 token 估算，比 web 准确 |

**结论**：桌面版是"本地优先版"的 web RAG——语义与命名对齐 web，实现换成 SQLite/FTS5，并在 BM25 真实性、重排、token 计量三处优于 web。

## 九、目标目录结构与数据模型

> **v3 核对补充（表结构）**：
> 1. `rel_path` 与 `index_state` 是页面功能的必要字段——文件树与文件夹层级（KP-18/KP-22）、「未索引 / 自定义索引」标记（KP-19）、文件夹重命名与删除（KP-24/KP-27）都依赖它们，v1 表结构只有 `name`/`status`，不足以支撑；
> 2. 磁盘仍按 `files/<kbId>/<docId>/<filename>` 隔离存储（重命名不改路径、`content_hash` 去重稳定），**文件树是逻辑结构**，由 `rel_path` 还原，不做磁盘目录镜像；
> 3. 文件夹重命名／删除 = 按 `rel_path` 前缀批量更新／删除文档行，并与磁盘目录、切片、向量、图谱级联。

**中文分词（关键设计）**：FTS5 的 `unicode61` 不做中文切词，整句会退化成一个 token。方案是写入前用 Electron 内置的 `Intl.Segmenter('zh', {granularity:'word'})` 分词、空格拼接后存入 `kb_chunk_fts.text_tokens`（contentless 表，rowid 对齐 `knowledge_base_chunks`），查询串同样先分词。

**零新增依赖**，已在 Node v24 实测：

```
知识库的向量检索与重排策略
  → 知识 | 库 | 的 | 向量 | 检索 | 与 | 重排 | 策略
```

优于引入 nodejieba（原生依赖）或改用 FTS5 trigram（召回质量差）。

### 10.2 主进程：`src/main/knowledge/ChunkingService.ts`（规划中）

| 策略 | 实现 |

### 10.3 主进程：`src/main/knowledge/IngestionPipeline.ts`（规划中）

单文档状态机，**阶段与进度完全沿用 web**：

```
queued(0) → parsing(3) → chunking(15) → embedding(30) → bm25(55)
          → extracting(70) → indexed(100)
                              ↘ failed(-1) / canceled
```

每步落库（`status` / `progress`）并推送 `knowledge:import-progress` 事件。

- **`maxUploadSize`**：`stat().size` 超限直接置 `failed`，不进入解析
- **`maxFilesPerBatch`**：在 IPC handler 层截断本次请求
- **`uploadTimeout`**：每个文档整段处理用 `Promise.race` 超时兜底，超时中止并记 `failed`
- **`graphEnabled`**：为真时才进入 `extracting` 阶段（与 web 一致：图谱失败不影响文档 `indexed`）
- 导入时把源文件复制进 `files/<kbId>/<docId>/<filename>`；sha256 命中同库已有哈希则复用，不重复建索引
- 无 embedding provider 时跳过 `embedding` 阶段（`chunking → bm25`），`chunk.embedding` 留 NULL

### 10.5 主进程：`src/main/knowledge/RetrievalService.ts`（规划中）

```ts
retrieve({ kbId, query, topK?, mode? }) → { hits: Hit[], rerankSkipped: boolean }
```

1. **稀疏**（`sparseRetrieval` 为真）：查询串分词后 `kb_chunk_fts MATCH`，`ORDER BY bm25(kb_chunk_fts, :k1, :b)` —— **`bm25K1` / `bm25B` 直接作为 FTS5 `bm25()` 辅助函数的实参**，是设置项与引擎最直接的一处对应
2. **稠密**（`EmbeddingProvider.available()` 为真）：查询向量化，取该库 `embedding IS NOT NULL` 的分块做 JS 内暴力余弦。本地量级（万级分块 × 1024 维 ≈ 40 MB）单次扫描在几十毫秒内，**不引 sqlite-vec 等原生扩展**，规避 Electron 跨平台打包负担
3. **融合**：两路各取 `topK` 候选，RRF（`RRF_K = 60`，对齐 web）加权版：`score = w/(60+rank_dense) + (1-w)/(60+rank_sparse)`，`w = hybridWeight`
4. **重排**（`rerankEnabled`）：POST OpenAI 兼容 `/rerank`；**未配置端点时为 no-op**，返回 `rerankSkipped: true` 供 UI 提示
5. 末段按 `topK` 截断，回带 `{chunkId, docId, docName, chunkIndex, content, score, vecScore, bm25Score}`（字段名对齐 web `search_api.py` 的 results）

## 十一、关键设计决策

> 状态：决策 1（索引库随 `knowledge.directory` 独立存放）、决策 6（表名与状态机对齐 web 的方向）、决策 7（全局配置 + 文档级快照的定位）在 v4 实施中已遵循；决策 2~5、8、9 属索引/检索阶段，待实现时遵循。

1. **索引库随 `knowledge.directory` 走**，不并入 `ke-work.db`：知识库是可重定位的独立存储，且分块/向量 blob 会撑大主库（主库还承载 LangGraph checkpoint）。

2. **不引向量库 / 原生扩展**：`embedding` 存 BLOB（`Float32Array`），检索时 JS 内暴力余弦。本地量级下延迟可接受，避免 sqlite-vec / FAISS 的 Electron 跨平台打包负担。后续若分块数超十万级，再评估 `loadExtension` 引入 sqlite-vec。

3. **RRF 加权而非分数加权求和**：BM25 分数量纲无界、与余弦 [-1,1] 不可比，min-max 归一小候选集下不稳定。沿用 web 的 `RRF_K = 60`，但让 `hybridWeight` 真正参与加权（web 的 alpha 只影响展示分，属设置虚设）。

4. **`Intl.Segmenter` 做中文分词**：零依赖、Electron 内置，配合 FTS5 `unicode61` 使用。

5. **`chunkSize`/`chunkOverlap` 以 token 计**：用轻量估算器（CJK 字符计 1，其余 `ceil(len/4)`）封装在 `estimateTokens()` 单点，后续可无痛替换为 `js-tiktoken`。

6. **表名与状态机对齐 web**：`knowledge_bases` 系列表名、7 阶段状态机与进度百分比全部沿用 web，使后续桌面↔WEB 对接退化为纯列映射；桌面额外多一张 `knowledge_base_chunks`（web 的分块在向量库里）。

7. **配置全局、快照落库**：桌面保持全局 `knowledge.*`（与已建成设置页一致），但在每个文档行记录生效配置快照，保证"重索引可复现"——等效 web 的每库/每文档配置覆盖能力。

8. **图谱抽取失败不阻断索引**：与 web 一致，`extracting` 阶段异常只记日志，文档仍进 `indexed`。

9. **降级对用户可见**：embedding / rerank 未配置时不静默失效，检索结果带 `rerankSkipped` 标记，设置页显示"向量检索未启用"提示。

| 按库覆盖 | 知识库页 → 条目三点菜单「知识库设置」/ 标题菜单「索引设置」 | `~/.ke-work/knowledge/kb-settings.json`（17 项稀疏覆盖） | 单个知识库 |

生效值与时机：

1. 生效值 = **全局值 ← 逐项覆盖**（主进程 `KnowledgeSettingsService.getEffective()`、渲染层 `effectiveFor()`）；
2. 设置页原文「修改后仅影响后续新增或重新索引的文件」——因此上传时要把生效配置写入 `knowledge_base_documents.config` 作为**文档级快照**，保证「重建索引可复现」；
3. 改配置**不会**自动重算历史文件，必须由用户对单文档或整库触发「重建索引」（KP-25）才会用上新配置；
4. 建议补一条串联动作：设置页保存成功后，若存在使用旧配置的文档，提示「已有 N 份文件仍使用旧配置，是否立即重建索引？」——这是把设置页与知识库页真正打通的一步。

### 13.4 核对结论：方案需随之修正的 6 点

| # | 问题 | 修正动作 |
| --- | --- | --- |
| 1 | v1 表结构缺少 `rel_path` 与 `index_state`，无法支撑文件树与「未索引／自定义索引」标记 | 已在第九章补列并加说明 |
| 2 | `knowledge:import` 只接受 `filePaths[]`，无法表达文件夹层级（KP-22） | 入参扩展为 `items: { srcPath, relPath }[]`（第十四章已更新） |
| 3 | `remove-doc` 是单文档语义，页面支持删除文件夹（KP-27） | 增加按 `rel_path` 前缀的批量删除语义 |
| 4 | `settingsStore.saveMany()` 是逐项 `config:set`（18 次 IPC），中途失败只回滚内存态 | 建议新增 `config:set-many` 批量写入（或单个事务），避免半保存 |
| 5 | `semantic` 切片与重排都依赖模型凭据，但设置页没有提示 | 「RAG 索引」「混合检索与重排」两张卡片增加「未配置模型时将降级为…」提示（v1 P2 第 14 项已列） |
| 6 | 「选择目录」立即落盘且不迁移旧库（`SettingsService.selectKnowledgeDir`），当前无二次确认 | 选择目录前增加确认：旧知识库将不可见，需手工迁回 |

## 十七、风险与待确认事项

| 类型 | 事项 | 建议 |
| --- | --- | --- |
| 口径冲突 | 桌面与后端在 `chunkSize` / `chunkOverlap` / `topK` / 默认值上不一致（5.3） | 先定一份共享契约再动代码，否则云端模式必然踩坑 |
| 语义差异 | `sparseRetrieval`（布尔） vs `sparse_algo`（枚举）、`graphModel` vs `entity_model`+`relation_model` | 优先「桌面改、后端不动」以保证云端一致 |
| 向量存储 | **已决策**：`embedding` 存 BLOB（Float32Array）+ JS 内暴力余弦，不引 sqlite-vec / FAISS（见第十一章第 2 条） | 仅当分块数超十万级时再评估 `loadExtension` 引入 sqlite-vec |
| 上传实现 | `<input type=file>` 与 `webkitdirectory` 在 Electron 下都拿不到绝对路径，必须走 `getPathForFile` | 已在 `PlusMenu.vue` / `NewTaskPage.vue` 验证可行 |
| 大文件 | 大文件复制 + 解析阻塞主进程 | 复制与解析放异步队列，避免阻塞 UI；必要时用 `worker_threads` |
| 数据迁移 | 现有 mock 知识库 ID（`product`/`design`…）在 `kb-settings.json` 中可能已有记录 | 首次启动做一次迁移：把 mock ID 的覆盖项映射到新建知识库，或直接清空并提示 |
| 命名一致性 | 页面中「索引设置」与「知识库设置」指同一功能；「知识库编辑」与「重命名」重叠 | 统一为「编辑」「索引设置」，降低用户困惑 |
| 权限 | 共享链接目前无权限模型 | P6 明确「只读 / 可下载 / 可编辑」与有效期 |

#### 18.7.1 「打开文件夹无反应」的排查与修复（v4.1 补）

**现象**：点击菜单项后界面没有任何反馈。

**根因**：渲染层 `window.api.*` 内部是 `ipcRenderer.invoke`，当主进程**没有注册该通道**时会 **reject**（典型场景：渲染层经 HMR 更新、但主进程仍是旧实例）。store 里直接 `await` 该 Promise，异常向上抛成未处理的 Promise rejection，界面既无 toast 也无日志——表现就是「点了没反应」。通道本身没有问题。

**修复**：

| 位置 | 改动 |
| --- | --- |
| `src/renderer/src/store/knowledge.ts` | 新增 `call()` 统一收敛：把 invoke 的 reject 转成 `{ success: false, error }`，15 个 IPC 调用全部走它；失败文案为「与主进程通信失败，请重启应用后重试（原始错误）」 |
| `src/renderer/src/views/KnowledgePage.vue` | 上传/上传文件夹里同步取真实路径（`getPathForFile`）加 try/catch，失败给出 toast，不再静默 |
| `src/main/index.ts` | `openDir` 失败时打印 `[knowledge] 打开文件夹失败: <path> <error>`；`showItemInFolder` 打印定位日志，便于对照排查 |

**验证**：真实应用内直接调用该通道返回 `{ success: true }`，知识库目录被创建，渲染层无未处理异常；新增 `tests/unit/store/knowledge.test.ts` 4 个用例覆盖「成功」「reject 不再静默」「主进程返回失败」「列表加载 reject 不抛异常」。

**给使用者的说明**：若看到「与主进程通信失败，请重启应用后重试」，说明当前运行实例的主进程早于该功能加入，**重启应用**（或让 dev 模式重启主进程）即可；界面已不会再出现无提示的情况。

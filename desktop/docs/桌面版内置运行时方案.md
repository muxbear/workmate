# 桌面版内置运行时方案

## 一、需求概述

在桌面版设置窗口「安全中心」页面的「内置运行时」模块中，展示 Python、Node.js、Git Bash 三个内置运行环境的状态与开关。这三个环境的安装路径对应「系统设置 → 存储 → ~/.ke-work 存储空间」路径下的 `binaries/` 目录，目录结构与 WorkBuddy 一致（`C:\Users\mux\.workbuddy\binaries`）。

## 二、现状分析

| 层面 | 现状 | 差距 |
|------|------|------|
| **UI 层** | `SecurityPage.vue` 已有「内置运行时」区块，`runtimeTools` 是硬编码 reactive 数组，有 Python/Node.js/Git Bash 三行 + 顶部总开关 | 数据是写死的，无版本号、无安装路径、无安装/卸载按钮、无真实状态 |
| **存储层** | `data-dir.ts` 管理基础目录 `~/.ke-work`，`SUB_DIRS` 目前只有 `logs/cache/workspace` | 无 `binaries` 子目录 |
| **设置 Schema** | `schema.ts` 白名单 13 个 key，无 runtime 相关 | 缺少 `runtime.enabled`、`runtime.python`、`runtime.node`、`runtime.git` 等键 |
| **IPC 层** | `config-handlers.ts` 有 `config:get-all`、`config:set` 等 | 无 `runtime:*` 通道 |
| **WorkBuddy 参考** | `C:\Users\mux\.workbuddy\binaries` 下有 `python/versions/3.13.12/python.exe`、`node/versions/22.22.2/node.exe`、`PortableGit/versions/1.2.0/bin/bash.exe`，及 `.cache/registry.json` 注册表 | — |

## 四、分层实现方案

### 1. 主进程：BinaryManager 服务

新建 `src/main/runtime/BinaryManager.ts`

```
职责：
- 管理 ~/.ke-work/binaries/ 目录的初始化与探测
- 读写 .cache/registry.json 注册表
- 探测已安装运行时版本（spawn 调用 --version）
- 触发安装/卸载（下载、解压、验证）
- 向渲染层提供运行时状态快照
```

核心类型设计：

```typescript
/** 运行时类型标识 */
type RuntimeId = 'python' | 'node' | 'git'

/** 运行时安装状态 */
type RuntimeStatus = 'not-installed' | 'installed' | 'verifying' | 'installing' | 'error'

/** 运行时信息（渲染层消费） */
interface RuntimeInfo {
  id: RuntimeId
  name: string                // 'Python' | 'Node.js' | 'Git Bash'
  description: string
  status: RuntimeStatus
  version?: string            // '3.13.12'
  executablePath?: string     // 绝对路径
  installPath?: string
  enabled: boolean            // 用户开关（来自 settings.json）
  error?: string              // 安装/验证失败信息
}
```

注册表结构（与 WorkBuddy 对齐）：

```jsonc
{
  "version": 1,
  "lastUpdated": 1787732205611,
  "binaries": {
    "python": {
      "3.13.12": {
        "source": "managed",
        "executablePath": ".../python/versions/3.13.12/python.exe",
        "installPath": ".../python/versions/3.13.12",
        "installedAt": 1787732204840,
        "verified": true
      }
    },
    "node": { ... },
    "git": { ... }
  }
}
```

关键方法：

- `init()` — 应用启动时调用，确保 `binaries/` 及各子目录存在
- `listRuntimes()` — 返回 `RuntimeInfo[]`（合并注册表 + 实时探测 + settings 开关状态）
- `detectRuntime(id)` — spawn 调用可执行文件 `--version`，返回版本号
- `installRuntime(id, version?)` — 下载压缩包 → 解压到 `versions/{version}/` → 验证 → 写注册表
- `uninstallRuntime(id)` — 删除版本目录 → 清注册表
- `getExecutablePath(id)` — 供 Agent 执行链路获取 Python/Node/Git 可执行文件路径

### 2. 主进程：RuntimeIPC 处理器

新建 `src/main/ipc/runtime-handlers.ts`

```
注册的 IPC 通道（均为 invoke，机器级，不调 session.requireUserId）：
- runtime:list        → BinaryManager.listRuntimes()
- runtime:install     → BinaryManager.installRuntime(id, version?)
- runtime:uninstall   → BinaryManager.uninstallRuntime(id)
- runtime:detect      → BinaryManager.detectRuntime(id)
```

在 `src/main/index.ts` 中注册：

```typescript
import { registerRuntimeHandlers } from './ipc/runtime-handlers'
// ...
registerRuntimeHandlers(ipcMain, { binaryManager, settingsService })
```

### 3. 主进程：Settings Schema 扩展

在 `src/main/settings/schema.ts` 中新增键：

```typescript
| 'runtime.enabled'
| 'runtime.python.enabled'
| 'runtime.node.enabled'
| 'runtime.git.enabled'
```

默认值：`runtime.enabled = true`，各子项 `enabled = true`（对齐 SecurityPage 当前 UI 的 `runtimeEnabled` 和 `runtimeTools[].enabled` 初值）。

### 4. 主进程：DataDirectory 扩展

在 `src/main/data-dir.ts` 中：

```typescript
export const SUB_DIRS = ['logs', 'cache', 'workspace', 'binaries'] as const
```

`BinaryManager` 通过 `getDataDirectory().getDir('binaries')` 获取 `~/.ke-work/binaries` 路径。

### 5. Preload 桥接

在 `src/preload/index.ts` 的 `api` 对象中新增：

```typescript
listRuntimes(): Promise<{ success: boolean; data?: RuntimeInfo[]; error?: string }> {
  return ipcRenderer.invoke('runtime:list')
},
installRuntime(id: string, version?: string): Promise<{ success: boolean; error?: string }> {
  return ipcRenderer.invoke('runtime:install', id, version)
},
uninstallRuntime(id: string): Promise<{ success: boolean; error?: string }> {
  return ipcRenderer.invoke('runtime:uninstall', id)
},
detectRuntime(id: string): Promise<{ success: boolean; data?: string; error?: string }> {
  return ipcRenderer.invoke('runtime:detect', id)
},
```

同时更新 `src/preload/index.d.ts` 中的类型声明。

### 6. 渲染层：Runtime Store

新建 `src/renderer/src/store/runtime.ts`

```
职责：
- onMount 调用 window.api.listRuntimes() 拉取初始状态
- 提供 toggle(id, enabled) → 调用 settingsStore.set('runtime.{id}.enabled', value)
- 提供 install(id) / uninstall(id) → 调用 IPC → 刷新状态
- 暴露 runtimes: Ref<RuntimeInfo[]>
```

### 7. 渲染层：SecurityPage.vue 改造

将现有硬编码的 `runtimeTools` 替换为从 `useRuntimeStore()` 读取：

**当前 UI 结构**（保留）：
- 面板标题「内置运行时」+ 描述「允许使用随包提供的 Node.js、Python 和 Git Bash 工具」+ 总开关 `SettingToggle`
- 表头三列：工具 | 说明 | 状态
- 三行运行时：Python（标记 Py）、Node.js（标记 JS）、Git Bash（标记 G）

**改造点**：

| 区域 | 改造内容 |
|------|----------|
| 数据来源 | `runtimeTools` → `runtimeStore.runtimes`（computed 映射） |
| 每行状态列 | 从 `SettingToggle` 改为状态标签 + 操作按钮组合：未安装显示「安装」按钮，已安装显示版本号 + 「卸载」按钮，安装中显示进度条/spinner |
| 版本显示 | 每行名称下方追加小字版本号 `v{version}`（已安装时） |
| 路径显示 | 可选：tooltip 或展开行显示 `executablePath` |
| 总开关 | 绑定 `settingsStore.set('runtime.enabled', value)`，关闭时三行置灰 |
| 安装进度 | 通过 IPC 事件流或轮询获取进度（可先做轮询，后续优化为事件流） |

**单行运行时的新交互**：

### 8. 运行时下载源与安装逻辑

参考 WorkBuddy 的安装方式，三种运行时的获取来源：

| 运行时 | 来源 | 格式 | 安装方式 |
|--------|------|------|----------|
| Python | python.org 官方嵌入式包 | zip | 下载 → 解压到 `python/versions/{version}/` |
| Node.js | nodejs.org 官方 Windows 二进制 | zip | 下载 → 解压到 `node/versions/{version}/` |
| Git Bash | git-scm.com PortableGit | zip | 下载 → 解压到 `PortableGit/versions/{version}/` |

安装流程（以 Python 为例）：

1. 用户点击「安装」→ `runtimeStore.install('python')` → IPC `runtime:install`
2. BinaryManager 执行：
   - 状态置为 `installing`
   - 下载压缩包到临时目录
   - 解压到 `~/.ke-work/binaries/python/versions/{version}/`
   - spawn 调用 `python.exe --version` 验证
   - 成功 → 写入 `.cache/registry.json`，状态置为 `installed`
   - 失败 → 清理残留，状态置为 `error`
3. 返回结果 → 渲染层刷新状态

### 9. Agent 执行链路集成（可选/后续阶段）

`BinaryManager.getExecutablePath(id)` 供 `AgentBuilder` 在构建工具链时使用：

- 当 `runtime.enabled` 且 `runtime.python.enabled` 为 true 时，Agent 的 Python 工具使用 `~/.ke-work/binaries/python/versions/{ver}/python.exe` 而非系统 PATH
- 同理 Node.js 和 Git Bash
- 当运行时被禁用或未安装时，回退到系统 PATH 检测

## 六、关键设计决策

1. **注册表与 WorkBuddy 对齐**：`.cache/registry.json` 结构完全复用 WorkBuddy 的 schema，便于未来互通或迁移。

2. **机器级配置**：运行时开关和安装状态不绑定用户 session，与 `config-handlers` 一致不调 `session.requireUserId()`，多用户共享同一套运行时。

3. **渐进式安装**：首版可以先实现「探测已有安装」+「安装/卸载按钮」，安装逻辑可用 workbuddy 已有二进制直接复制（从 `~/.workbuddy/binaries/` 复制到 `~/.ke-work/binaries/`）作为快速验证，后续再接入在线下载。

4. **状态轮询 vs 事件流**：首版用安装后重新拉取 `listRuntimes()` 的方式刷新状态；后续可优化为 IPC 事件流推送安装进度。

5. **总开关语义**：`runtime.enabled = false` 时，三行运行时置灰且 Agent 不使用内置运行时，但已安装的二进制不删除。

## 七、测试策略

- **单元测试**：`BinaryManager` 的注册表读写、版本探测逻辑（mock spawn）
- **集成测试**：在临时目录（`KE_WORK_HOME` 指向 tmp）中测试完整安装→探测→卸载流程
- **E2E**：打开设置 → 安全中心 → 内置运行时 → 验证状态显示与开关交互
